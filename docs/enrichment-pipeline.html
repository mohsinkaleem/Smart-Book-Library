01 · Organising principle

Two rules the whole pipeline turns on

Everything else — the stages, the scoring, the caching — is machinery in service of these two constraints. They are what make “a bad API match silently replaced good local metadata” structurally impossible rather than individually patched.

Rule one

A field is never written without its source and confidence

BookRecord.set_field() is the only sanctioned way to write a bibliographic field. It refuses a write from a source that ranks below whatever wrote the field last, and it stamps field_sources[name] = {source, confidence, at} alongside every value it accepts.

catalog/models.py:120

Rule two

An external match must be verified, not merely returned

The old flow took docs[0] / items[0] and applied it unconditionally, so a bad query was guaranteed to produce a confidently wrong record — and the wrong ISBN it wrote then “confirmed” the wrong book on the next run. Now every candidate is scored against local evidence before anything is applied.

02 · End to end

The map

Nine stages run per book, in a fixed order, across a thread pool (MAX_WORKERS, default 4). Five closing stages then run once per run, inside a finally block — so an interrupted run still leaves a consistent catalog rather than an un-deduplicated one.

03 · Collect

Evidence: what we know before we ask anyone

Nothing is queried until the pipeline has assembled its own account of what the file is. collect_evidence() builds an Evidence object from four local sources, and every title clue keeps a label saying where it came from — because that label decides which clue is trusted and which query is worth making.

SourceYieldsRank as a title clueModule

Text is split three ways, not one

A single text_excerpt used to serve as reader preview, embedding input and evidence at once. For two thirds of the catalog its opening characters are a copyright page — so summaries described copyright pages, and unrelated books looked similar to each other because their boilerplate matched.

front_matter    pages 1–5, max 3,000 chars   → evidence only, never embedded
content_sample  first page scoring ≥400 prose → embedded + summarised
                chars, TOC pages skipped
text_excerpt    first 5,000 chars            → reader preview

The front-matter trap

real page 1
Muhammad Asad
THE ROAD TO
MECCA

Other Works by Muhammad Asad
THE MESSAGE OF THE QURAN
ISLAM AT THE CROSSROADS
SAHIH AL-BUKHARI: THE EARLY YEARS…

A title page advertises the publisher's other books, and any ISBN printed beside them belongs to those books. This is why an ISBN hit that contradicts a strong title page is downgraded to partial rather than trusted at 1.0.

The gate before the gate: is there enough to search on?

Three files in this library are called Aisha.pdf, 757.pdf and 1658134075976.pdf. The correct behaviour for them is to stay unenriched — not to accept whatever a search engine returns for a one-word query. So a title search requires ≥2 non-stopword tokens and ≥8 characters, or the record is flagged and no request is made at all.

// catalog/evidence.py — Evidence.title_is_searchable()
"Aisha"                     → tokens=1  ✗ no search   flag: insufficient evidence
"757"                       → tokens=0  ✗ no search
"The Road To Mecca"         → tokens=3  ✓ searchable
"Catcher on Rye"            → tokens=3  ✓ searchable

8 records in the current catalog sit in the review queue for exactly this reason.

04 · Ask

Candidates: both providers, always, field-scoped

Evidence becomes queries in a fixed order — ISBN lookups first (identity is cheap when you have it), then title/author searches. Both OpenLibrary and Google Books are queried every time: a weak first answer from one must not prevent a strong answer from the other being considered.

Queries are field-scoped. A flat concatenated string is what once let aisha adobe indesign cs5.5 return an InDesign manual.

// catalog/api_enricher.py — gather_candidates()
for isbn in evidence.isbns[:2]:
    openlibrary_by_isbn(isbn)      GET /api/books?bibkeys=ISBN:…&jscmd=data
    google_books_by_isbn(isbn)     GET /volumes?q=isbn:…

for title in evidence.query_titles(limit=2):   at most one clue per source class
    openlibrary_search(title, author)          ?title=…&author=…      (never one flat q)
    google_books_search(title, author)         ?q=intitle:"…" inauthor:"…"

    // retry without the author only when THIS title found nothing with it
    if author and no title_author hits:
        openlibrary_search(title); google_books_search(title)

Two title clues, not one

Searching only the strongest clue is fragile. A mangled title page yielding "Muhammad Asad MECCA" would bury a filename that says "The Road To Mecca" outright — so one clue per source class gets its own query.

Per-host token buckets

Google Books' anonymous quota is small and per-IP, so four workers hitting it in parallel earn a 429 on every call. Hosts are throttled independently (0.4/s anonymous, 1.0/s with a key), and a 429 starts a 45-second cool-down instead of burning the remaining requests on guaranteed failures.

A cache with an explicit status

Entries are {status, fetched_at, payload}. error is never reused; not_found expires after 30 days. A transient connection reset is no longer a permanent “this book does not exist”. Legacy statusless entries are dropped on load.

Counters that make a dead provider visible

Per-source attempted / ok / not_found / error / throttled / cached, printed every run, with an alert above a 20% error rate. The original catalog had OpenLibrary contributing zero records for months without a single log line.

05 · Verify

The verification gate

Every candidate from every provider is scored against the evidence. An ISBN hit is identity and short-circuits to 1.0. Otherwise the score is a weighted blend of title, author and year similarity — renormalised over the dimensions we actually have evidence for, so a record with no author evidence is not silently capped below the acceptance threshold.

Title-only evidence raises both bars

With no author and no year to corroborate, accept moves to 0.85 and partial to 0.60. The thresholds were measured against the catalog's known mismatches (0.17–0.53) versus its genuine matches (0.85–1.00), so a partial overlap of common words — “Perspectives on …” — cannot claim a relationship.

An ISBN can be overruled

An ISBN match normally returns 1.0. But if the title page carries a substantial clue (≥3 significant tokens) that scores below 0.35 against the candidate, the verdict drops to partial with the reason recorded: “the identifier may belong to another book listed in the front matter.”

Borderline can be adjudicated by a local LLM

Under --llm, a 0.45–0.75 candidate is put to Ollama with the local clues and the candidate record: same book, yes or no? It must answer with ≥0.60 confidence to count. 54 records in the current catalog were saved from a wrong match this way.

Rejections are recorded, not discarded

Up to five rejected candidates are stored on the record with their provider, score and reason — so “why did this book get nothing?” is answerable months later without re-running anything.

06 · Merge

The merge: rank decides, confidence breaks ties

A verdict does not write anything by itself. Each field goes through set_field(), which compares the incoming source's rank against whatever wrote that field last. Higher rank wins outright; equal rank replaces only an empty value or a strictly more confident one; and user is never overwritten by anything.

field currently written by ← incoming

Identity fields vs descriptive fields

A borderline match may write only description, page_count and language. It may never write title, authors, isbn_10/13, publication_year or publisher — a wrong identifier corrupts dedupe and every later lookup.

…and never a cover

The cover is the most visible field in the UI, so a borderline match never supplies one. A children's-book jacket on a da'wah pamphlet reads as fact long before anyone opens the review queue.

The truncation guard

OpenLibrary's ISBN record for Understanding Salafism is titled just Salafism. Accepting it would replace a correct, fuller title with a poorer one purely because the match was verified — so a candidate title that is a strict substring of the current one is skipped.

_ratio("Understanding Salafism", "Salafism") = 0.813 — high enough to pass, wrong to apply.

External subjects never become facets

Provider subjects land in subjects_raw, kept verbatim and searchable through FTS. Only the analyzer's controlled vocabulary may write categories — which is how 51 labels over 120 books, 27 of them used exactly once, became a fixed list of 15.

08 · Describe

Local analysis: categories, themes, summaries, vectors

Identity settled, the remaining stages describe the book. These write at low rank — analyzer 20, llm 25 — so nothing here can disturb a verified bibliographic field.

analyze · density-normalised scoring

Scoring used to sum raw occurrence counts over corpora whose length varies by two orders of magnitude, so a long excerpt that merely mentions “statistics” outranked a short one actually about it.

score = Σ  field_weight × specificity          title 6.0 · subtitle 4.0
     +  3.0 × specificity × min(hits,5)      subjects 4.0 · desc 2.5
             ─────────────────────           publisher 0.5
             len(body) / 2000                specificity = 1 + 0.75×(words−1)

gates:  score ≥ 3.0        and
        field_hits > 0     or  ≥3 distinct keywords in body alone

The second gate is why a file with no metadata is no longer confidently assigned both “Computer Science” and “Islam & Islamic Studies”: one repeated word in the text is not a subject.

llm · where a model is actually strong

optional · --llm

Summarising the content sample — never the copyright page. The prompt is refused if the passage is mostly boilerplate.

Choosing from an enum — the category list is pasted into the prompt with “copy the label verbatim; if none fit, return an empty list.” It selects, it does not invent.

Adjudicating borderline matches — the one place its judgement outranks arithmetic.

Writing a description where no provider had one — which is why llm is the single largest source in the catalog: 490 of 571 descriptions.

Ollama, qwen3.5:4b by default, serialised to one generation at a time. Unreachable → the stage is skipped with a warning, never a failure.

embed · batched, and deliberately not the front matter

optional · --embed

Two vectors per book: one over the content sample (for “find books like this”) and one over assembled metadata (title, authors, themes, categories, keywords, summary). Encoding one record at a time is 10–50× slower than a batch, so the per-book stage only queues the record — the whole run is encoded in one pass at the end and written to the embeddings table as float32 blobs.

09 · Close

Closing stages

These run once, after the per-book pass, inside a finally block. An interrupted run — Ctrl-C halfway through 600 books — still deduplicates, reconciles and saves. A narrowed run (--only, --max, --type) scopes the per-record closing stages to the files it actually touched; dedupe stays global by design, because a newly added book's twin may be anywhere in the catalog.

Deduplication in three phases

1 · content hash   same SHA1, different paths          byte-identical copies
2 · trusted ISBN   source ∈ {user, isbn_match, file_meta, filename, front_matter}
                  or api_verified with confidence ≥ 0.75
                  ↳ an unverified ISBN may not establish identity — that is how
                    false ISBNs from unverified matches would merge unrelated books
3 · fuzzy title    token_sort_ratio ≥ 90, blocked on shared long tokens,
                  and corroborated by author, year (±1) or page count (±5%)

canonical = max(metadata_completeness, has_text, size)

Identity is file_path; content_sha1 is an attribute. When records were keyed by hash, two byte-identical files silently overwrote each other and the collision became invisible — and the grouping branch that was supposed to mark duplicates could never execute.

10 · Re-run

Resumability, and the delicate half of it

Every stage carries a version in STAGE_VERSIONS. A stage runs when its version is newer than the version stored on that record, when the file's content hash changed, or under --force. Everything else is skipped — which makes re-running cheap and makes “re-run just the LLM stage” a one-line config change.

Invalidation is the delicate half. Two rules keep a partial re-run from silently destroying data:

  • A stale stage drags its dependents along. analyze cannot keep categories derived from a description that enrich is about to replace.
  • A re-running stage first withdraws what it previously wrote. Otherwise the stale value outranks the fresh one through SOURCE_RANK and is never replaced. Output from a stage that is not re-running is left alone — which is why --no-api no longer erases verified metadata.

Bump a stage version — see what re-runs

Metadata cohort

parse · extract · ocr · identify · enrich all write the same bibliographic fields and settle conflicts by rank, so they are invalidated together. Re-running enrich while skipping parse would drop the filename title with nothing to restore it.

Dependency graph

analyze ← extract, ocr, enrich · llm ← analyze · embed ← extract, ocr, enrich, analyze. Staleness spreads transitively to a fixed point.

11 · The human loop

What the gate cannot settle, a person does

11% of records were wrong and there was no way to see that, and no way to correct one. Records the gate could not confirm now surface at /review in the web app and through GET /api/review/queue, least certain identity first.

A correction posted to /api/review/{id}/pin is written three places at once: the value onto the books row, a stamp of {source: "user", confidence: 1.0} into field_sources, and the value into user_data.field_overrides — which is re-applied on every write, so a full rebuild cannot destroy it.

Why 220 records are queued

The pin, end to end

POST /api/review/<id>/pin
{ "field": "title", "value": "The Catcher in the Rye" }

    ↓
books.title            = "The Catcher in the Rye"
books.field_sources    += { "title": { "source": "user", "confidence": 1.0 } }
user_data.field_overrides += { "title": { value, at } }

    ↓ next pipeline run, next --force, next full rebuild
set_field("title", …, "api_verified", 0.92)   → refused
    prev.source == "user" → return False

15 fields are pinnable — title, subtitle, authors, publisher, year, both ISBNs, language, description, summary, categories, themes, keywords, cover. The pipeline never writes the user_data table at all.
